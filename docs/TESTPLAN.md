# COBOL Accounting System Test Plan

This plan validates the business behavior currently implemented by the COBOL prototype and provides a baseline for the Node.js transformation. `Actual Result`, `Status`, and `Comments` are intentionally left for stakeholder execution and sign-off.

| Test Case ID | Test Case Description | Pre-conditions | Test Steps | Expected Result | Actual Result | Status (Pass/Fail) | Comments |
|---|---|---|---|---|---|---|---|
| TC-001 | Start a new application run | The application is not running. | 1. Compile and start the application. 2. Observe the initial menu. | The account balance is initialized to `1000.00`. The account-management menu displays options 1 through 4 and prompts for a choice. |  |  |  |
| TC-002 | View the initial balance | A new application run is active. | 1. Select option `1`. | The application displays `Current balance: 1000.00`. The balance is unchanged and the menu is displayed again. |  |  |  |
| TC-003 | View the balance after a credit | The application is active with a balance of `1000.00`. | 1. Select option `2`. 2. Enter `250.00`. 3. Select option `1`. | The credit is accepted and the application displays a new balance of `1250.00`. The subsequent inquiry also displays `1250.00`. |  |  |  |
| TC-004 | View the balance after a debit | The application is active with a balance of `1000.00`. | 1. Select option `3`. 2. Enter `250.00`. 3. Select option `1`. | The debit is accepted and the application displays a new balance of `750.00`. The subsequent inquiry also displays `750.00`. |  |  |  |
| TC-005 | Credit a zero amount | The application is active with a balance of `1000.00`. | 1. Select option `2`. 2. Enter `0.00`. 3. View the balance. | Per the current implementation, the credit is accepted, the displayed balance remains `1000.00`, and the value is written to storage. Stakeholders should confirm whether the Node.js app should preserve or reject zero credits. |  |  |  |
| TC-006 | Credit an amount with cents | The application is active with a balance of `1000.00`. | 1. Select option `2`. 2. Enter `10.25`. 3. View the balance. | The application displays and stores `1010.25`; two decimal places are retained. |  |  |  |
| TC-007 | Debit exactly the available balance | The application is active with a balance of `1000.00`. | 1. Select option `3`. 2. Enter `1000.00`. 3. View the balance. | The debit is accepted because the balance is greater than or equal to the requested amount. The new balance is `0.00`. |  |  |  |
| TC-008 | Debit less than the available balance | The application is active with a balance of `1000.00`. | 1. Select option `3`. 2. Enter `999.99`. 3. View the balance. | The debit is accepted and the new balance is `0.01`. |  |  |  |
| TC-009 | Reject a debit greater than the available balance | The application is active with a balance of `1000.00`. | 1. Select option `3`. 2. Enter `1000.01`. 3. View the balance. | The application displays `Insufficient funds for this debit.` No write occurs and the balance remains `1000.00`. |  |  |  |
| TC-010 | Reject a debit from a zero balance | The application is active with a balance of `0.00`, for example after TC-007. | 1. Select option `3`. 2. Enter `0.01`. 3. View the balance. | The debit is rejected with the insufficient-funds message. The balance remains `0.00`. |  |  |  |
| TC-011 | Debit a zero amount | The application is active with a balance of `1000.00`. | 1. Select option `3`. 2. Enter `0.00`. 3. View the balance. | Per the current implementation, the debit passes the sufficient-funds check, displays a successful debit, writes the unchanged balance, and leaves the balance at `1000.00`. Stakeholders should confirm whether the Node.js app should preserve or reject zero debits. |  |  |  |
| TC-012 | Attempt a credit that would exceed the numeric field capacity | The application is active with a balance of `999999.00` or another value close enough to overflow the `PIC 9(6)V99` field. | 1. Select option `2`. 2. Enter an amount that produces a result above `999999.99`. 3. View the balance and record the runtime behavior. | The current COBOL field supports up to six whole-number digits and two decimal places. Stakeholders must define whether the Node.js app should reject the transaction with a validation error, support a larger value, or match the COBOL overflow behavior. |  |  |  |
| TC-013 | Enter an invalid menu choice below the valid range | The application is active. | 1. Enter menu choice `0`. | The application displays `Invalid choice, please select 1-4.` The account is not changed and the menu is shown again. |  |  |  |
| TC-014 | Enter an invalid menu choice above the valid range | The application is active. | 1. Enter menu choice `5`. | The application displays `Invalid choice, please select 1-4.` The account is not changed and the menu is shown again. |  |  |  |
| TC-015 | Select exit | The application is active. | 1. Enter menu choice `4`. | The application ends the menu loop and displays `Exiting the program. Goodbye!` |  |  |  |
| TC-016 | Confirm multiple transactions use the latest stored balance | The application is active with a balance of `1000.00`. | 1. Credit `100.00`. 2. Debit `40.00`. 3. View the balance. | Each successful transaction reads the current stored balance before calculating. The final balance is `1060.00`. |  |  |  |
| TC-017 | Confirm a rejected debit does not affect a later transaction | The application is active with a balance of `1000.00`. | 1. Attempt to debit `1000.01`. 2. Credit `50.00`. 3. View the balance. | The rejected debit leaves the balance unchanged. The credit uses `1000.00` as its starting value, so the final balance is `1050.00`. |  |  |  |
| TC-018 | Confirm balance inquiry does not affect later transactions | The application is active with a balance of `1000.00`. | 1. View the balance. 2. Credit `25.00`. 3. View the balance again. | The first inquiry returns `1000.00`; the credit is calculated from that balance; the second inquiry returns `1025.00`. |  |  |  |
| TC-019 | Confirm storage resets after application restart | Complete a credit or debit so the balance differs from `1000.00`, then exit. | 1. Restart the application. 2. Select option `1`. | The current implementation stores the balance only in working storage, so a new process starts again at `1000.00`. Stakeholders should confirm whether Node.js must instead persist the balance. |  |  |  |
| TC-020 | Call the data module READ operation | The data module is available for an isolated component test. | 1. Initialize storage to its default. 2. Call `DataProgram` with operation `READ`. 3. Inspect the returned balance. | The module copies the stored balance (`1000.00` by default) into the caller's balance field and does not alter storage. |  |  |  |
| TC-021 | Call the data module WRITE operation | The data module is available for an isolated component test. | 1. Set the caller's balance to `1234.56`. 2. Call `DataProgram` with operation `WRITE`. 3. Call `READ`. | `WRITE` replaces stored balance with `1234.56`; a subsequent `READ` returns `1234.56`. |  |  |  |
| TC-022 | Call the data module with an unsupported operation | The data module is available for an isolated component test. | 1. Set a known stored balance. 2. Call `DataProgram` with an operation other than `READ` or `WRITE`. 3. Call `READ`. | The current implementation performs no action for an unsupported operation; no error is displayed and the stored balance remains unchanged. Stakeholders should decide whether Node.js should reject unsupported operations explicitly. |  |  |  |
| TC-023 | Enter a nonnumeric menu value | The application is active. | 1. Enter a nonnumeric value such as `X` at the menu prompt. 2. Record whether the program rejects the input, redisplays the menu, or terminates. | The current source only defines numeric input behavior. The observed COBOL runtime behavior must be documented and a Node.js validation rule agreed with stakeholders. |  |  |  |
| TC-024 | Enter a nonnumeric transaction amount | The application is active. | 1. Select option `2` or `3`. 2. Enter a nonnumeric value such as `ABC`. 3. Record the application behavior and final balance. | The current source only defines numeric amount behavior. The observed COBOL runtime behavior must be documented and a Node.js validation rule agreed with stakeholders. |  |  |  |
| TC-025 | Enter a negative transaction amount | The application is active. | 1. Select option `2` or `3`. 2. Attempt to enter a negative amount. 3. Record the application behavior and final balance. | The amount field is unsigned (`PIC 9(6)V99`), and the current code has no explicit positive-amount validation. Stakeholders must define whether negative input is rejected and ensure the Node.js implementation does not unintentionally turn a credit into a debit or a debit into a credit. |  |  |  |
